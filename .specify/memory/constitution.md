# Terraform AzureRM Modules Constitution

## Core Principles

### I. Azure First

This repository MUST contain reusable Terraform modules for Azure services (including Microsoft
services delivered on Azure such as Microsoft Fabric and Microsoft Purview) and MUST NOT contain
modules for other clouds.

- Each module MUST wrap one Azure service, or one tightly coupled set of Azure resources, and be
  usable on its own.
- Provider selection MUST follow this order: the `azurerm` provider first, the `azapi` provider
  when `azurerm` does not yet expose the required resource or property, and the Microsoft Fabric
  provider for Fabric items. Last-mile automation (Principle IV) is the final option.
- Modules MUST use Azure-native capabilities (Microsoft Entra ID, managed identities, Azure RBAC,
  Azure Monitor, Private Link) rather than third-party equivalents.
- Module inputs and outputs MUST use Azure terminology and resource identifiers (for example
  `resource_group_name`, `location`, resource IDs) so modules compose without translation.

Rationale: Azure-native modules stay aligned with the platform's security, networking, and
operations model and remain simple to consume and maintain.

### II. Documentation for All Content

Every artifact in `modules/` MUST be documented so that a consumer can use it without reading its
source.

- Each module MUST have `README_header.md`, `README_footer.md`, and a `README.md` generated by
  terraform-docs using the repository `.terraform-docs.yml`.
- Every `variable` and `output` MUST have a `description` that states purpose, allowed values, and
  the effect of changing it (including when it forces resource replacement).
- Each module header MUST describe what the module deploys, its secure defaults, and every
  security exception (see Principle III).
- Each script under a module `scripts/` folder MUST state its purpose, parameters, and required
  permissions in a header comment (comment-based help for PowerShell).
- The root `README.md` MUST list every module in `modules/` with a link to its folder.
- Changes to variables, outputs, defaults, or behavior MUST update the affected documentation in
  the same pull request.

Rationale: These modules are consumed by other teams; undocumented inputs, defaults, and exceptions
are indistinguishable from defects.

### III. Secure by Default (NON-NEGOTIABLE)

Every module MUST deploy in its most secure supported configuration when only required inputs are
supplied.

- Public network access MUST be disabled by default, with private connectivity provided through
  Private Link private endpoints where the service supports them.
- Authentication MUST use Microsoft Entra ID and Azure RBAC. Shared keys, local authentication,
  access policies, and anonymous access MUST be disabled where the service allows.
- Encryption in transit (current minimum TLS version, HTTPS only) and at rest MUST be enabled, and
  protection features such as soft delete and purge protection MUST be enabled where available.
- Diagnostic settings MUST be supported and enabled for services that expose logs or metrics.
- Secrets MUST NOT be hard-coded, committed, or output in plain text. Variables and outputs that
  carry secrets MUST be marked `sensitive = true`.
- Insecure settings MUST NOT be exposed as a convenience. Where a variable relaxes a secure
  setting, its default MUST be the secure value.
- An exception is allowed only when the secure setting blocks critical functionality of the Azure
  service. Each exception MUST be (a) as narrow as possible, (b) explained by a short inline code
  comment, and (c) documented in the module README header with the setting, the reason, and the
  recommended mitigation.

Rationale: Insecure defaults propagate into every consumer deployment; secure defaults with
explicit, documented exceptions keep the risk visible and deliberate.

### IV. Terraform for Infrastructure, PowerShell and Azure CLI for Last-Mile Automation

Terraform MUST declare all Azure infrastructure. PowerShell (`pwsh`) and Azure CLI MUST be the only
mechanisms used for last-mile automation, meaning steps that Terraform providers cannot express.

- Last-mile steps are limited to operations without provider support, such as approving managed
  private endpoint connections or assigning workspaces to a domain.
- Before adding a last-mile step, the author MUST confirm that neither `azurerm` nor `azapi` can
  perform the operation.
- Last-mile steps MUST run through a `local-exec` provisioner with
  `interpreter = ["pwsh", "-Command"]`, with `on_failure = fail`, and with scripts stored in the
  module `scripts/` folder. Azure CLI commands MUST be called from PowerShell.
- Scripts MUST be idempotent, MUST use the ambient Azure identity of the Terraform run, and MUST
  NOT embed or accept credentials as plain-text arguments.
- The triggering `terraform_data` or `null_resource` MUST define triggers so that re-runs happen
  only when the relevant inputs change.
- Other scripting languages (for example Bash or Python) MUST NOT be used for last-mile
  automation.

Rationale: Declarative Terraform provides drift detection and reviewability; limiting scripting to
one shell and one CLI keeps the unavoidable imperative code small and consistent.

## Technology and Repository Constraints

- Each module MUST live in `modules/<name>/` and declare its provider requirements in
  `terraform.tf`. Where a module uses `azurerm`, it MUST be constrained to major version 5
  (`~> 5.0`).
- Module files MUST follow the existing layout, using only the files that apply: `terraform.tf`,
  `variables.tf`, `main.tf`, `outputs.tf`, `data.tf`, `connectivity.tf`, `diagnostics.tf`,
  `roleassignments.tf`, `scripts/`, and `tests/`.
- Modules MUST NOT configure provider blocks. CI pins provider versions for tests by copying
  `code/utilities/terraform_override.tf` into the module under test.
- Test setup modules MUST reference sibling modules by relative local path and MUST NOT use remote
  `?ref=main` sources.
- Terraform code MUST pass `terraform fmt -check -recursive`.
- The `archive/` folder is not authoritative and is not governed by this constitution.

## Development Workflow and Quality Gates

- All changes MUST be made through pull requests; the PR description MUST list the proposed
  changes.
- Each module MUST have a `tests/test.tftest.hcl` that runs with `terraform test`, and a workflow
  `.github/workflows/terraform-<module>.yml` that calls `_terraformTestTemplate.yml`.
- CI MUST authenticate to Azure with OIDC and MUST NOT use stored credentials. GitHub Actions MUST
  be pinned to a full commit SHA.
- A new module MUST add, in the same pull request: the module folder with documentation (Principle
  II), tests, a CI workflow, a `terraform-docs-go` hook and README exclusion entry in
  `.pre-commit-config.yaml`, and a link in the root `README.md`.
- Changes that rename or remove variables or outputs, or change a default in a way that alters
  deployed resources, MUST be called out as breaking in the pull request description.
- Reviewers MUST verify compliance with Principles I to IV before approving.

## Governance

This constitution supersedes other practices and conventions in this repository. Where a module
conflicts with it, the module MUST be corrected or the deviation MUST be recorded as a documented
exception under Principle III.

- **Amendments**: Amendments MUST be made by pull request that edits this file, states the
  rationale, and lists affected modules, workflows, or templates that need follow-up changes.
- **Versioning**: This constitution uses semantic versioning. MAJOR is for backward-incompatible
  removals or redefinitions of principles or governance. MINOR is for a new principle or section,
  or materially expanded guidance. PATCH is for clarifications and wording fixes.
- **Compliance review**: Every pull request review MUST check compliance with the principles above.
  Reviewers MUST reject undocumented security exceptions. Unjustified complexity MUST be removed or
  justified in the pull request.
